# GAS 프로젝트 개발 플레이북 (Development Playbook)

> **언제 읽나**: GAS(Apps Script) 프로젝트를 **새로 시작**하거나 **리팩토링·기능 추가**하기 전에. 코드를 짜기 전에 먼저.
> **무엇을 다루나**: 실제 프로젝트에서 깎아온 **설계 원칙·재사용 패턴·실패 카탈로그·플랫폼 한계 판단**. 도구 사용법(clasp·JS 문법·HTML)이 아니라 **"왜 이렇게 설계해야 하나"**.
> **읽고 나면**: 이미 검증된 패턴을 재사용하고, 이미 겪은 함정(가짜 알람·재시도 폭주·dedup 누수·차단)을 **다시 만들지 않으며**, "이 요구사항은 GAS로 되는가, 떠나야 하는가"를 판단할 수 있다.

> **이 문서는 AI(LLM)가 읽고 단독으로 개발을 진행할 수 있게 쓰였다.** 메모리·컨텍스트가 없는 상태에서 이 문서만 읽어도 올바른 판단이 가능하도록, 각 규칙에 **왜(이유)**와 **거부한 대안**을 함께 적는다.

---

## 0. 이 문서를 읽는 법 (AI를 위한 규약)

- **🧭 근본 원칙** = 인프라가 바뀌어도(Vercel·Node·DB로 가도) **유지**할 것. 설계의 뼈대.
- **🔧 GAS 제약 산물** = GAS의 한계 때문에 만든 우회. 인프라가 바뀌면 **버리거나 치환**할 것.
- **규칙은 "명령형 + 이유" 형식**이다. 이유 없이 따르지 말 것 — 이유가 안 맞는 상황이면 규칙도 안 맞는다.
- **"거부한 대안"** 항목은 우리가 시도했다 버린 설계다. **다시 제안하지 말 것.**
- 사례는 `projects/kingshot-coupon`(킹샷 쿠폰 자동 발급)을 인용하지만, **교훈은 일반화**해서 적는다.

## 1. 핵심 원칙 (모든 GAS 프로젝트의 출발점)

### 🧭 1.1 멱등성 (Idempotency) — 같은 작업을 두 번 해도 안전하게

GAS 트리거는 **재실행·이어실행·중복 실행**이 일상이다(6분 한도·자동 재시도·수동 재실행). 따라서 모든 부수효과(외부 API 호출, 시트 쓰기)는 **"이미 했으면 건너뛴다"**가 기본이어야 한다. → 패턴 A(dedup) 참조.

### 🧭 1.2 격리 (Isolation) — 옵션 기능은 본체를 절대 깨뜨리지 않는다

선택적/실험적 레이어(외부 소스 동기화, 부가 알림 등)는 **통째로 삭제해도 본체가 멀쩡**해야 한다. 모든 진입점을 `try/catch`로 감싸 **어떤 예외도 트리거 밖으로 던지지 않는다**. "꺼놨을 때와 똑같이 동작"이 격리의 정의. → 패턴 E.

### 🧭 1.3 외부 의존 최소화 — 받아쓰되 저장하지 않는다

외부 데이터(커뮤니티 소스의 만료일 등)는 **그 순간 판단에만 쓰고 시트에 영속 저장하지 않는다**. 외부 스키마 변경이 우리 상태를 오염시키지 못하게. 우리 상태의 진실은 **항상 우리 자신의 검증/응답**에서 온다.

### 🧭 1.4 단일 진입점 — "사람이 손으로 한 것"과 동일 경로

자동화(스케줄 동기화 등)가 만드는 등록도 **수동 등록과 똑같은 함수**를 거치게 한다. 그러면 검증·dedup·캐시·배치 로직을 **한 곳에만** 두면 되고, 자동 경로가 새로운 상태 오염을 만들 수 없다.

## 2. 재사용 설계 패턴

각 패턴: **문제 → 해법 → 거부한 대안 → 사례**.

### 패턴 A — 멱등 dedup (terminal-state 집합) 🧭

**문제**: 트리거 재실행/이어실행 때 이미 처리한 작업을 또 호출하면 → API 낭비 + 로그 무한 누적 + 중복 부수효과.

**해법**: 처리 로그에서 **"확정(terminal) 상태"만** 모은 집합을 만들어, 그 안에 있는 `(대상, 작업)` 조합은 건너뛴다.

- terminal = 더 시도해도 결과가 안 바뀌는 상태: `SUCCESS`, `ALREADY_USED`(이미 받음), `CONDITION_NOT_MET`(자격 미달 — 영구적).
- **non-terminal = 일시 상태는 집합에 넣지 않는다**: `RATE_LIMITED`, `ERROR`, 일시 네트워크 실패 → 다음 실행에서 **자연히 재시도**됨(따로 재시도 패스 불필요).

```js
function getProcessedSet_() {
  const set = new Set();
  for (const row of logRows) {
    if (
      row.result === 'SUCCESS' ||
      row.result === 'ALREADY_USED' ||
      row.result === 'CONDITION_NOT_MET'
    ) {
      set.add(`${row.id}|${row.job}`);
    }
  }
  return set; // 이 집합에 있으면 skip(무료·무API), 없으면 처리
}
```

**거부한 대안**:

- ❌ "성공만 dedup" → `ALREADY_USED`를 다시 시도해 매 배치 API 폭주 + 가짜 알람. **이미 받음도 terminal로 보존**해야 한다.
- ❌ "실패도 dedup에 넣어 영구 skip" → 일시 실패를 영구 포기하게 됨. 일시 상태는 **반드시 재시도 대상**.

**함정 (실측)**: 로그 시트를 cap 회전(오래된 행 삭제)할 때 **terminal 행을 지우면 dedup 진실이 깨져** "영원히 유효한 작업"이 매 배치 재처리되는 무한 루프. → 회전 시 **terminal 상태는 절대 삭제 금지**, non-terminal(노이즈)만 회전.

**사례**: kingshot `getProcessedSet_` / `rotateNoiseLogs_`.

### 패턴 B — 외부 API 회복력 (transient vs terminal 분류) 🧭

**문제**: 외부 API의 응답 코드를 잘못 분류하면 → 일시 오류를 영구 실패로 처리(손해)하거나, 미매핑 코드가 전부 "에러"로 떨어져 **가짜 알람 + 재시도 폭주**.

**해법**: 모든 응답을 **명시적으로 분류**하고, 분류마다 행동을 정한다.

| 분류            | 의미                          | 행동                                                                              |
| --------------- | ----------------------------- | --------------------------------------------------------------------------------- |
| 성공            | 완료                          | terminal, dedup 보존                                                              |
| 이미 처리됨     | 중복 요청(부수효과 이미 발생) | **terminal**, dedup 보존, 재시도/알람 X                                           |
| 자격 미달(영구) | 이 대상엔 영구히 불가         | **terminal**, dedup 보존, 재시도/알람 X (단 작업 자체는 유효 → 작업 비활성화는 X) |
| 무효/만료       | 작업 자체가 죽음              | terminal, **작업 단위 비활성화** + 관련 로그 purge                                |
| 레이트리밋/일시 | 잠깐 막힘                     | **non-terminal**, 백오프 후 재시도                                                |
| 인증 필요       | 선행 호출 필요                | 선행 후 재시도(self-heal)                                                         |

**거부한 대안**:

- ❌ "매핑 안 된 코드는 그냥 ERROR" → ERROR는 보통 (a) 경고 카운터↑ = **가짜 봇/IP 알람**, (b) dedup 미보존 = **매 배치 재시도**. **새 API/새 코드 도입 시, 그 코드가 ERROR 버킷에 떨어지는지 항상 점검**하고 적절한 terminal/transient로 매핑.

**함정 (실측)**: "같은 타입 보상 이미 보유"(부수효과는 전달됨)가 미매핑→ERROR로 떨어져 난리. 자격 미달(레벨/등급 부족)도 마찬가지. → 둘 다 **terminal로 분류**해 폭주 차단.

**HTTP/차단 처리**: `429`·`5xx`는 재시도 대상. `200`인데 본문이 HTML(`<html`/`cf-ray`/`cloudflare`)이면 **공유 IP 차단 페이지**일 수 있으니 하드에러가 아니라 **일시(재시도)**로 다뤄라(→ 패턴 B는 §4 egress와 연결).

**사례**: kingshot `Api.js > classifyResponse_`.

### 패턴 C — 장시간 작업 = 시간예산 + 자동 이어실행 🔧(GAS 6분 한도 우회)

**문제**: GAS 실행은 **6분 제한**. 대량 작업(N대상 × M작업 × 지연)은 한 번에 못 끝낸다.

**해법**: **시간예산(예: 5분)**을 두고, 초과하면 **안전 중단 → 1분 뒤 자기 자신을 재예약(트리거)**. 다음 실행은 **dedup(패턴 A)으로 이미 한 건 건너뛰고 이어서** 처리. 작업이 한 실행 예산에 다 들어올 때까지 이게 반복되며 **수렴**한다(매 실행 일부가 terminal이 되어 남은 일이 줄어듦).

```
while (대상) {
  if (now - start > 시간예산) { 1분뒤_재예약(); return; } // 안전 중단
  if (processed.has(키)) continue;                        // dedup skip(무료)
  처리();                                                  // 지연 + API
}
```

**거부한 대안**:

- ❌ "고정 N회 이어실행" → 작업량을 모르면 부족하거나 과함. **dedup 기반 동적 이어실행**이 정답(끝나면 자연 종료).
- ❌ "지연을 줄여 6분 안에 욱여넣기" → 외부 API 봇감지 위험(→ 패턴 B/§4). **지연이 레이트 거버너**다.

**⚠️ 알아둘 비대칭**: 시간초과 이어실행은 보통 **상한이 없다**(끝날 때까지 반복). 일시 오류(RATE_LIMITED)는 dedup 제외라 매 이어실행에서 재시도되는데, 정상 상황에선 곧 terminal이 되어 멈춘다. 하지만 **지속적 외부 장애**(공유 IP가 계속 막힘)면 이어실행이 길게 갈아낼 수 있다 → 그건 retry 튜닝 문제가 아니라 **§4 egress-off-GAS 신호**다. (모니터링: 한 작업에 이어실행 5회↑ 또는 매 실행 경고>0 연속)

**사례**: kingshot 배치(`유저 × 쿠폰`, 5분 예산 → 1분 재예약).

### 패턴 D — 알림 = 엣지 트리거 + 백스톱 자동 OFF 🧭

**문제**: 고빈도 폴링/배치에서 실패할 때마다 알림을 쏘면 → **노이즈 폭탄**(하루 24번). 반대로 실패를 침묵시키면 → **조용한 고장**(기능이 죽어도 모름).

**해법 1 — 엣지 트리거 알림**: **상태 전이에서만** 알린다. 정상→실패 **1회**, 실패→복구 **1회**. 지속 실패 중엔 침묵(로그엔 매번 기록). 직전 상태를 영속 저장(예: `LAST_RESULT.ok`)해 비교.

**해법 2 — 백스톱 자동 OFF**: 옵션 기능이 **연속 N회(영구 death 임계, 예: 1주일치)** 실패하면 **자동으로 끄고 1회 알림**. 성공 1회로 카운터 리셋 → **일시 장애는 self-heal, 진짜 영구 고장만 종료**. 임계는 보수적으로 크게(일시 outage가 절대 못 넘게).

**거부한 대안**:

- ❌ "매 실패 알림" → 노이즈. **엣지로 dedup**.
- ❌ "실패 완전 침묵" → 조용한 고장. 최소 전이 1회는 알려야.
- ❌ "일시 실패 1번에 자동 OFF" → self-heal 죽임. 자동 OFF는 **높은 연속 임계**일 때만.

**카운터 저장 위치**: GAS 트리거는 매 실행이 새 isolate라 메모리 변수가 사라진다. **연속 실패 카운터는 영속 저장소(Script Properties 등)에 read-modify-write** 해야 다음 실행이 읽는다. (🔧 Properties는 GAS 산물 — 다른 인프라면 KV/DB row로 치환)

**사례**: kingshot `Sync.js`(엣지 알림 + 168회 연속 실패 자동 OFF).

### 패턴 E — 옵션 레이어 격리 🧭

**문제**: 부가 기능(외부 동기화 등)의 오류가 본체(핵심 등록·배치)를 망가뜨리면 안 됨.

**해법**: 옵션 레이어는 (1) **전 진입점 try/catch**, (2) 각 외부 호출도 독립 try/catch, (3) **단일 진입점(원칙 1.4)에만 위임** — 자기 상태를 직접 안 만짐, (4) **기본 OFF**, (5) 본체와 코드 경로 완전 분리(파일 통째 삭제해도 무손상).

**검증 질문**: "이 레이어 파일을 지금 `rm` 하면 본체가 멀쩡한가?" → 아니면 격리 실패.

**사례**: kingshot `Sync.js`(통째 삭제해도 수동 등록·배치 100% 정상).

## 4. 🔧 GAS 제약 vs 🧭 근본 원칙 — 인프라 이식성

> **이 절의 목적**: 미래에 이 프로젝트를 Vercel·Node·DB 등 **다른 인프라로 옮길 때**, 무엇을 버리고(🔧) 무엇을 지킬지(🧭) 즉시 판단하기 위함. 설계 전에 "이 요구사항이 GAS로 되는가"를 먼저 점검하라.

### 4.1 GAS 플랫폼 한계 (코드로 우회 불가 — 설계 전 점검)

**네트워크 (`UrlFetchApp`)** 🔧

- egress가 **구글 공유 IP 풀**을 탄다 → 외부가 IP 평판/봇 검사를 하면 **차단될 수 있음**. (실측: Discord webhook이 Cloudflare에 지속 차단됨)
- **프록시·IP 고정 불가** — 차단당해도 GAS 안에서 IP를 바꿀 방법이 없다.
- 외부 API에 **캡차 / IP 화이트리스트 / 레이트리밋(429)** 이 있으면 GAS에서 막히기 쉽다.

**런타임** 🔧

- **npm 런타임 패키지 불가**(순수 JS만), 빌드 없음(TS/JSX 불가).
- **네이티브 바이너리 / WASM / ONNX / OCR 실행 불가** — 이미지 처리·ML 추론을 GAS 안에서 못 한다.
- **실행 6분 제한**(→ 패턴 C로 우회), 동시성은 `LockService`로 직렬화.

### 4.2 GAS로 충분 ✅ vs 떠나야 함 🚨

| GAS로 충분 ✅           | egress-off-GAS 필요 🚨                   |
| ----------------------- | ---------------------------------------- |
| 시트 기반 자동화·소규모 | 외부 API가 IP평판/캡차/화이트리스트 검사 |
| 평판 안 따지는 공개 API | Discord 등 GAS-차단 서비스 알림          |
| 이미지/ML/OCR 불필요    | ONNX·OCR·네이티브 연산 필요              |
| 간헐적·저빈도 호출      | 대량·저지연·정기 고빈도                  |

### 4.3 탈출구 — egress-off-GAS 릴레이

한계에 걸리면 **외부 호출을 GAS 밖 작은 릴레이로 분리**한다. GAS는 시트+웹UI로 남고, 릴레이가 외부 API를 대신 호출.

- 가벼운 전달(예: Discord 알림) → Cloudflare Workers / Vercel 함수 **무료 티어로 충분**.
- 무거운 연산(예: 캡차 OCR/ONNX) → Python 가능한 서버리스(Vercel Fluid 등) 또는 상시 컨테이너(Fly.io·Railway·VPS).
- 릴레이 IP(데이터센터)도 또 차단되면 → residential 프록시 추가.

### 4.4 배포형 앱의 자동 업데이트 — 라이브러리로 안 된다 🧭(설계 초기 판단)

"시트를 복사해 나눠주는" 배포 모델에서 **원본을 고치면 전원 자동 반영**은 **불가능**하다.

- GAS 라이브러리는 버전 고정(수동 bump+재배포)이거나, HEAD 모드(소비자에 edit 권한 필요=위험)뿐.
- **HTML/웹앱은 라이브러리화 자체가 불가**(백엔드 `.gs`만, `doGet`·`*.html` 못 넣음).
- **진짜 자동 업데이트 = 중앙 백엔드 하나**(=한 곳 운영 + 공유 데이터 = egress-off-GAS 영역).
- → "자동 업데이트 필요?"가 요구사항에 있으면 **복사 모델이 아니라 중앙 백엔드로 설계**하라.

> 배포 메커니즘(복사/라이브러리/중앙 백엔드 결정 매트릭스, /dev vs /exec 반영, 다중 배포자 전략)의 **실행 상세**는 별도 배포 가이드 문서가 다룬다. 이 플레이북은 **"어느 모델을 고를지"라는 판단**까지만 책임진다.

### 4.5 이식 매핑 (GAS → 다른 인프라)

| GAS 산물 🔧                                                  | 다른 인프라에선                                                           |
| ------------------------------------------------------------ | ------------------------------------------------------------------------- |
| 5분 예산 + 1분 이어실행, 동적 재예약                         | 300s+ 함수 / Queue / Workflow(durable step) — 한 번에 처리 또는 단계 분할 |
| Script Properties 카운터(스트릭·재시도)                      | env / KV / DB row                                                         |
| 시간 트리거(`everyHours`)                                    | Cron                                                                      |
| `CacheService`(dead-code 캐시 등)                            | KV / Redis                                                                |
| 공유 IP 레이트 거버너(지연+jitter)·차등 재시도·egress 릴레이 | 전용/회전 IP → 거의 불필요(지연 대폭↓ 가능)                               |
| 시트 dedup(`getProcessedSet_`)                               | DB unique/upsert                                                          |
| HtmlService 웹앱 + 인라인 i18n                               | 표준 프론트(Next.js 등) + i18n                                            |
| 시트 카피 배포(트리거·설정 복사 안 됨 = zero-setup)          | 멀티테넌트(완전 다른 모델)                                                |

**🧭 이식해도 유지되는 것**: 멱등 dedup, transient/terminal 분류, err_code 매핑 점검, 격리 원칙, 엣지 알림 + 백스톱, 단일 진입점, 외부의존 최소화. **이건 인프라와 무관한 설계 원칙이다.**

## 5. 체크리스트

**새 GAS 프로젝트 시작 전**

- [ ] 요구사항이 §4.2의 🚨 열에 걸리나? → 걸리면 처음부터 egress-off-GAS/중앙 백엔드 검토
- [ ] 외부 API가 캡차/IP평판/429를 쓰나? → 패턴 B + §4 대비
- [ ] 대량/장시간 작업이 있나? → 패턴 C(시간예산+이어실행) 설계
- [ ] "복사 배포 + 자동 업데이트" 요구? → §4.4: 라이브러리 X, 중앙 백엔드

**외부 API 연동 시**

- [ ] 모든 응답을 terminal/transient로 **명시 분류**했나? 미매핑이 ERROR로 안 떨어지나? (패턴 B)
- [ ] 멱등한가? 재실행해도 중복 부수효과 없나? (패턴 A)
- [ ] 일시 실패에 백오프 재시도 + 영구 실패엔 백스톱이 있나? (패턴 B·D)

**부가/옵션 기능 추가 시**

- [ ] 이 파일을 `rm`해도 본체가 멀쩡한가? (패턴 E 격리)
- [ ] 전 진입점 try/catch? 기본 OFF? 단일 진입점에만 위임? (패턴 E)
- [ ] 알림은 엣지 트리거인가? 지속 실패에 백스톱 자동 OFF인가? (패턴 D)

**배포 직전**

- [ ] 트리거(HEAD)와 웹앱 /exec(배포본) 반영 경로를 구분했나?
