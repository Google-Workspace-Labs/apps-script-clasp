# GAS 웹앱 — 외부 자산 내장 & 배포 반영 가이드

> Apps Script HtmlService 웹앱에서 ① **외부 이미지를 외부 의존 없이 내장**하는 법과
> ② **수정한 UI가 사용자에게 실제로 반영되게** 하는 배포 모델을 정리한다.
> kingshot-coupon 프로젝트에서 실제로 검증한 내용 기반.

---

## 1. 외부 이미지를 base64 데이터 URI로 내장하기

### 1-1. 왜 내장(embed)인가

Apps Script HtmlService 는 **단일 HTML 파일 + 인라인 CSS** 구조다. 외부 이미지를 쓰는 방법은 둘:

| 방식 | 동작 | 평가 |
|---|---|---|
| **A. 직접 링크(hotlink)** | `url('https://남의-cdn/img/...png')` | ❌ 외부 의존. 상대가 파일을 바꾸거나(특히 **해시 파일명** `home_bg.ec0d99a1.png`) 내리면 **깨짐**. 남의 CDN 트래픽 사용. |
| **B. base64 내장(권장)** | `url('data:image/jpeg;base64,/9j/4AAQ...')` | ✅ **자기완결**. 네트워크 요청 0·CORS 0·외부 변경에 사이드이펙트 0. 파일에 박혀 영구 보존. |

> **핵심:** base64 데이터 URI 는 "외부 요청"이 아니라 **그냥 HTML 안의 텍스트**다.
> `clasp push` 가 HTML 파일을 통째로 올리므로 base64 문자열도 그냥 같이 올라가고,
> HtmlService iframe 이 렌더할 때 외부 호출 없이 그대로 그려진다. `UrlFetchApp` 같은 것도 불필요.

### 1-2. 제약은 "파일 크기" 하나뿐

- GAS HTML 파일 한도는 넉넉하다(수백 KB~MB). 배경 1~2장 + 로고 = **수백 KB 내장은 문제없음**.
- base64 는 원본보다 **약 1.33배** 커진다 (3바이트 → 4문자).
- 그래도 큰 원본은 **반드시 리사이즈/재압축**해서 넣는다. (아래 1-3)

### 1-3. 자산 최적화 (macOS `sips` 기준)

원본이 1920×1080 PNG(557KB)처럼 과하면 **표시 용도에 맞게 줄인다.** 게임 일러스트/사진은 PNG보다 **JPEG**가 훨씬 작다(화질 손실 거의 안 보임). 로고처럼 **투명 배경**이 필요하면 PNG 유지하되 표시 크기로 축소.

```bash
# 배경: JPEG 변환 + 가로 1200px + 품질 74  → 557KB(png) → 145KB(jpg)
sips -s format jpeg -s formatOptions 74 -Z 1200 home_bg.png --out bg_web.jpg

# 로고: 투명 유지(PNG) + 가로 480px 로 축소  → 319KB(3267px) → 68KB(480px)
sips -Z 480 logo.png --out logo_small.png

# base64 인코딩 (줄바꿈 제거해 한 줄로!)
base64 < bg_web.jpg | tr -d '\n' > bg_web.b64
```

> `-Z N` = 긴 변을 N px 로 맞춰 비율 유지 리샘플. `formatOptions` = JPEG 품질(0~100).
> `tr -d '\n'` 으로 **줄바꿈을 반드시 제거**한다 (CSS `url()` 안은 한 줄이어야 안전).

**실측 예 (kingshot-coupon):** 웹배경 193KB + 모바일배경 78KB + 로고 90KB = base64 **약 362KB**, index.html 최종 **414KB**. 정상 동작.

### 1-4. 거대 문자열을 HTML 에 주입하기

base64 문자열은 수십~수백 KB라 손으로 못 붙인다. **스크립트로 주입**한다 (Node 예시):

```js
const fs = require('fs');
const path = 'projects/<app>/index.html';
let html = fs.readFileSync(path, 'utf8');
const b64 = fs.readFileSync('/tmp/bg_web.b64', 'utf8').trim();

// 기존 body 배경 블록을 정확히 찾아 교체 (고유 문자열 매칭)
html = html.replace(OLD_BG_CSS, `background: url('data:image/jpeg;base64,${b64}') center / cover fixed;`);
fs.writeFileSync(path, html);
```

> ⚠️ 주입 후 `prettier` 는 **건너뛰는 게 안전**할 수 있다(수백 KB 한 줄 처리가 느릴 수 있음).
> 단, pre-commit 훅의 prettier 는 데이터 URI 를 한 줄로 보존하므로 커밋은 통과한다.

### 1-5. 반응형 배경 (모바일/데스크탑 전환)

두 배경을 모두 내장해두고 **CSS 미디어쿼리**로 전환한다 (디바이스 판별은 클라이언트가).

```css
/* 기본 = 모바일(세로) 배경 */
body {
  background:
    linear-gradient(rgba(10, 22, 34, 0.18), rgba(10, 22, 34, 0.18)), /* 가독성 오버레이 */
    url('data:image/jpeg;base64,<MOBILE>') center top / cover no-repeat fixed;
}
/* 데스크탑 = 가로 배경 */
@media (min-width: 601px) {
  body {
    background:
      linear-gradient(rgba(10, 22, 34, 0.18), rgba(10, 22, 34, 0.18)),
      url('data:image/jpeg;base64,<WEB>') center / cover no-repeat fixed;
  }
}
```

**가독성 팁:** 화려한 배경 위에선 카드/패널을 **불투명**으로 유지하고, 배경에 **살짝 어둡게(또는 밝게) 오버레이** 한 겹(`linear-gradient(rgba(...,0.18), ...)`)을 깔면 글자가 선명해진다.

> 참고: `background-attachment: fixed` 는 iOS Safari 에서 `scroll` 처럼 동작(고정 안 됨). 치명적이지 않음.

### 1-6. ⚠️ 저작권 주의

공식 게임/서비스의 **배경·로고는 해당 사 IP**다. 지인용 비공개 도구라면 현실적 리스크는 낮지만 **정식 라이선스는 아니다.** 공개 배포·상업화 시 주의.

## 2. 배포 반영 모델 — 수정이 "사용자에게" 보이게 하기

GAS 웹앱에서 가장 헷갈리는 지점. **코드를 올렸는데 사용자 화면은 그대로**인 함정의 원인.

### 2-1. 두 종류의 URL

| URL | 별칭 | 무엇을 서빙 | 누가 접근 |
|---|---|---|---|
| `…/exec` | **버전 배포(production)** | **고정 버전 스냅샷** | 배포 설정대로(예: 누구나) |
| `…/dev` | **테스트 배포(HEAD)** | **항상 최신 저장 코드** | **스크립트 편집 권한자만**(소유자/에디터) |

- **`/dev` = node dev 모드 같은 것.** 코드 저장(=`clasp push`) 후 **새로고침만 하면 즉시 반영**. 재배포 불필요.
  단, **편집 권한이 있는 사람(보통 본인)만** 열 수 있다 → 개발/검증용.
- **`/exec` = 사용자(친구)용.** **특정 버전 번호에 고정**되어, 그 버전을 새로 만들어 연결하기 전엔 **아무리 push 해도 안 바뀐다.**

> 그래서 "내 `/dev` 에선 되는데 친구 `/exec` 에선 안 보인다" 가 발생한다.
> 개발 중엔 `/dev` 로 빠르게 확인하고, **사용자 반영은 `/exec` 재배포가 별도로 필요**하다.

### 2-2. `clasp push` ≠ 배포

`clasp push` 는 **HEAD(프로젝트 내용)만** 갱신한다. `/dev` 는 바뀌지만 `/exec` 는 안 바뀐다.

### 2-3. `/exec` 를 최신으로 — URL 유지하며 새 버전 연결

가장 흔한 실수: UI `배포 ▸ 새 배포` 에서 **버전 드롭다운을 "새 버전" 으로 안 바꾸면** 옛 버전이 그대로 재배포된다.
또 `새 배포` 로 만들면 **URL 이 새로 생겨** 기존 사용자 링크가 깨진다.

**확실한 방법 — clasp 로 기존 배포 ID 를 새 버전으로 갱신 (URL 그대로):**

```bash
# 1) 배포 목록 + 현재 버전 확인
clasp list-deployments
#  - AKfyc…HEAD          @HEAD   ← /dev (테스트)
#  - AKfyc…(친구용 ID)   @51     ← /exec (production, 옛 버전 고정)

# 2) HEAD 최신화
clasp push -f

# 3) 그 배포를 HEAD 기준 '새 버전' 으로 재배포 (versionNumber 생략 = HEAD)
clasp deploy -i <친구용_배포ID> -d "변경 요약"
#  → Deployed <ID> @52   (URL 동일, 내용만 최신)
```

> `clasp deploy -i <id>` 는 `--versionNumber` 를 생략하면 **HEAD 로 새 버전을 만들어 그 배포에 연결**한다.
> 같은 배포 ID = **같은 `/exec` URL** → 친구 링크 안 깨지고 최신 반영.

### 2-4. 그래도 안 보이면 = 캐시

`/exec` HTML 은 브라우저·구글 CDN 이 캐시한다. 재배포 후:
- **강력 새로고침**(Cmd/Ctrl+Shift+R) 또는 **시크릿창**으로 확인.

### 2-5. 배포 반영 체크리스트

```
[ ] clasp push -f                    # 코드 업로드(HEAD)
[ ] /dev 새로고침으로 본인 확인       # 즉시 반영(편집권한자만)
[ ] clasp deploy -i <exec배포ID>     # 사용자용 새 버전 연결(URL 유지)
[ ] clasp list-deployments 로 @버전↑ 확인
[ ] /exec 강력 새로고침/시크릿창 확인  # 캐시 우회
```

## 3. 다중 배포자(복사본) 업데이트 전략

2장은 "내 앱 하나"의 `/exec` 최신화였다. 그런데 이 시트를 **여러 명이 복사해 각자 배포**하면
새 문제가 생긴다 — **"원본을 고치면 그 사람들 전원에게 자동 반영되나?"**

> **결론(한 줄): GAS 라이브러리로는 "자동 반영" 불가. 진짜 자동 업데이트는 중앙 백엔드뿐.**

### 3-1. GAS 라이브러리 사실 (오해 방지)

- **버전 고정(v5, v6…)**: 자동 반영 ❌. 원본이 v6 를 내도 소비자는 v5 그대로 →
  **소비자가 버전 번호를 수동으로 올리고 재배포**해야 함. (소비자가 view 권한이면 이 방식뿐)
- **HEAD(개발 모드)**: 런타임에 최신 HEAD 사용 → 자동 반영되나 **소비자에게 라이브러리 edit 권한 필요**
  (배포 대상에게 주기엔 위험·부적합) + **느림**(dev 모드).
- ⚠️ **HTML/웹앱은 라이브러리화 불가**: `doGet`·`*.html`(클라 UI)은 라이브러리에 못 넣는다.
  넣을 수 있는 건 **백엔드 `.gs` 함수만** → **UI 수정은 라이브러리로 전파 자체가 안 됨**.
- 라이브러리가 새 OAuth 스코프를 추가하면 소비자 **재인증** 필요.

### 3-2. 배포 모델 결정 매트릭스

| 모델        | 자동 전파              | HTML 커버 | 데이터           | 노력         |
| ----------- | ---------------------- | --------- | ---------------- | ------------ |
| 복사(copy)  | ✗                      | —         | 각자 시트        | 낮음         |
| +라이브러리 | △ (수동 bump·백엔드만) | ✗         | 각자             | 중간         |
| 중앙 백엔드 | ✓                      | ✓         | 공유 저장소 필요 | 높음(재설계) |

### 3-3. 권장

- **소규모 나눔**: 복사 모델 유지 + **"버전 알림"** — 각 복사본이 트리거 때 중앙 manifest
  (GitHub raw 또는 작은 시트)에서 최신 버전 번호를 fetch → 구버전이면 배포자에게
  Slack/메뉴로 "새 버전 있음" 안내. **감지=자동, 적용=수동**(re-copy / `clasp pull`). 가성비 최고.
- **대규모/정기**: **중앙 백엔드**(egress 를 GAS 밖 — Cloud Run 등 — 으로, 데이터도 공유 저장소).
  스케일(공유 IP rate limit)과 유지보수(한 곳만 고치면 전원 반영)를 **동시에** 해결.

## 요약

- **이미지 내장**: 외부 링크 대신 `sips` 로 최적화 → base64 → CSS `url(data:...)` 로 박으면 **외부 의존 0**·영구 보존.
- **배포 반영**: `/dev`(HEAD, 즉시·편집권한자만) vs `/exec`(버전 고정, 사용자용). `clasp push` 만으론 `/exec` 안 바뀜 → **`clasp deploy -i <배포ID>`** 로 URL 유지하며 새 버전 연결.
- **다중 배포자**: 라이브러리로는 자동 반영 불가(버전고정=수동·HTML 제외·edit권한 필요). 소규모는 복사+버전알림, 대규모는 중앙 백엔드.
